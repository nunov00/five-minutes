### Bounded reviewer execution failures

A spawn failure, interruption, timeout or aborted/incomplete review is an execution failure, not an editorial verdict or an editorial revision round. Record its stable failure signature using the schema below, PR/head, policy commit, child/dispatch IDs and actual evidence in the existing append-only dispatch ledger. Reconcile complete records across scheduled runs before another spawn. Permit at most ONE retry of the same execution failure, and only after recording a concrete mitigation or newly available capability/evidence. No mitigation means checkpoint without a new child. Count attempts across parents and dates; a new dispatch key, scheduled opportunity or candidate SHA does not reset a recurring setup/read-order/tool failure. A changed head still requires a fresh full review when eligible, but cannot bypass this cap on the same execution failure.

Each ledger entry stores `failure_signature` as the exact string `STAGE|CAPABILITY|CAUSE|RESOURCE`, alongside separate free-text `evidence` and `mitigation` fields. Use only these values: STAGE = `SPAWN`, `POLICY_READ`, `BRIEF_AUDIT`, `ELIGIBILITY`, `SOURCE`, `RENDER`, `FEEDBACK`, `MERGE` or `RECONCILIATION`; CAPABILITY = `DELEGATION`, `GITHUB_READ`, `POLICY_READ`, `SOURCE_FETCH`, `PAGE_RENDER` or `GITHUB_WRITE`; CAUSE = `UNAVAILABLE`, `ACCESS_DENIED`, `INCOMPLETE`, `ORDER_VIOLATION`, `MISMATCH`, `EXPIRED`, `INTERRUPTED`, `TIMEOUT` or `UNKNOWN`. RESOURCE is the lowercase tool name, trusted-policy repository-relative path, public source hostname or renderer engine, as applicable; omit variable URLs, PR/head/dispatch IDs and clocks. Equality is byte-for-byte equality of these four canonical fields, never similarity of prose. Reuse an existing applicable signature; a new wording, head or dispatch cannot rename it. If the evidence does not map unambiguously, use `UNKNOWN`, record the competing existing signatures and block further spawning until Manager classification; do not invent a fresh key to gain another retry. Legacy free-text records need Manager classification before retry, not a fresh budget.

After that retry fails for the same cause, append EXECUTION BLOCKED and report once for Manager diagnosis. Later scheduled runs inspect actual state and exit without spawning again for that cause until the Manager records a verified remedy and explicitly releases this execution block. Never relax the policy read order, feedback retrieval, source/render review or merge gates to make a retry succeed. Do not create extra tasks or commission repeated same-provider reviews of maintenance policy. Existing expiry, overlap, editorial-round and technical-recovery limits continue independently.

Remove only that parked key from the shortlist, recording a temporary shortfall if needed. Do not modify other shortlist briefs, lesson files, facts, acceptance criteria, priorities, identities, other pool entries, code, policy, schema or checks. Use a normal maintenance branch/PR without editorial-review-requested and follow GOVERNANCE's applicable classification, review, exact-head checks and expected-head merge; no lesson-only exception or earlier Ready record authorises this PR. The authoring run cannot act as its own review. This is the same ordinary Manager repair path as other narrow maintenance, not extra publication merge authority.
4. Once the reviewed parking change merges, later Writer selection advances to the next queued item; it can never silently mark the parked lesson accepted, covered or complete. If required access, checks or review blocks the queue-only PR, report that specific recovery gate and leave it reviewable; do not resume daily failed content attempts, bypass it or claim publishing has recovered. Queue parking is not lesson publication and does not consume a new daily content slot, but an already-attempted day still permits no second candidate.
5. Parked entries retain all content and provenance. Returning one requires an Owner instruction or new evidence resolving the issue, a stated reason and a normal reviewed Manager queue PR. Owner return clears the blocker and uses priority 0. Keep the blocker issue linked to the recovery history and record the resolution. Parked work remains in the full pool and is reported once with its blocker; eligible ranked new ideas may proceed without discarding it.

An Owner-return/parking PR advances main. If merged while a candidate is open, that candidate is stale and cannot be replaced the same day; the daily slot may be lost. Prefer merging non-urgent queue administration after the current release completes. Urgent Owner instructions still take precedence, with the same fail-closed stale-candidate rule.
